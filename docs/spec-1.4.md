## 1 现状（实测，不是估计）

实境现在是一块黑，三层原因缺一层都解释不完。

第一层是开关：`REAL_SYSTEM.look` 是 `{ ...REAL_PROTO.look, orbitLines: true }`，`decor: false` 是从
`REAL_PROTO` 继承来的，而星空挂在 `look.decor` 上。所以实境根本没挂这一层。

第二层是量纲：`SKY_RADIUS = 820`（`starfield.ts`）是给沙盘世界单位定的，而米制相机在 1e7–1e13 m 上工作，
`tightenClipPlanes` 给的 near 在 d=1e7 时已经是 2441 m（`near = clamp(d/4096, 0.06, d/1.25)`）。
820 的世界单位球整个落在近平面里面，翻开关也只会得到一片黑。

第三层是量级：「恒星在太阳系尺度内没有视差」这句话是对的，所以整片天空挂在跟随相机的 group 上。
这层机制本身正确，缺的是**半径从哪来**——它现在是一个常量。

亮度基线：清屏色 `#07090e` 的相对亮度 8.94；上一次 verify 里 `proto-real` 的画布网格除地球占的三块
之外全是 8.9，也就是「实境 = 清屏色」有读数。对照组是沙盘：同一份 verify 的 `zoom-budget.sky`
量到边缘 12 块均值 18.56，是背景的 2.08 倍。

## 2 决策 1 实境星空层

**结论：** 天球半径从 `far` 反推，`天球半径 = far / 1.2`；`SphereGeometry` 与 `createStarGeometry()`
一次建好，每帧只写一个 `group.scale`。`SKY_RADIUS = 820` 从「世界半径」降级成「几何体单位半径」，
值不动，语义变了。

**数字：**

1. **和 820 的关系是恒等式，不是替换。** 沙盘的 `far = max(1.25d, 16384 × near, farFloor)`，
   overview 档 `near = 0.06`，所以 `far = 16384 × 0.06 = 983.04`；`983.04 / 1.2 = 819.2`。
   现在的 820 与 819.2 只差 0.8 m（0.0976%），我猜当初是上取整；不管当初怎么算的，
   `far / 1.2` 在沙盘里复现现状值。沙盘一个像素都不会动：天球是纯方向场，顶点着色器用
   `normalize(position)` 取方向，星点的 `gl_PointSize` 也不除深度；银河带的噪声按**未缩放的 `position`**
   在顶点里算，缩放只进 modelMatrix，不会让带子重算。

2. **1e16 m 下的精度代价：0.000063 px。** d = 1e16 时 `near = 2.44e12`、`far = 4e16`、
   天球半径 3.33e16。float32 在 3.33e16 处的最小间隔 2.15e9 m，折成方向误差
   `2.15e9 / 3.33e16 = 6.4e-8 rad`；42° 视场 / 720 行下 1 px = 1.018e-3 rad，所以 6.3e-5 px。
   它比抖动阈值 0.35 px 小 5500 倍，比现存噪声底 0.067 px 小 1060 倍。代价不在顶点上，
   在 `group.scale`：float32 标量的相对误差 6.4e-8，与顶点同一个量级。天空层不引入新的精度问题。

3. **内存与顶点预算（一次性，不随量级变）。** 星点 2800 颗 × 4 属性 = 89.6 KB；
   天球 192×96 段 = 18,721 顶点 / 36,864 三角、顶点 599 KB + 索引 221 KB = 820 KB。
   合计 910 KB、21,521 顶点、2 个 draw call，跨九个量级不变——换的是 `group.scale`，不是几何体。
   顺手一条：`SphereGeometry` 带的 normal 与 uv 这两个着色器不用，自建几何只留 position 能省 374 KB。
   **明确否掉**：每次视距变化重建 `SphereGeometry`，那是每次 820 KB 重传 + 36,864 三角重算。

4. **`clipFar` 必须无条件写。** `tightenClipPlanes` 现在只在 near/far 变化超过 5% 时才写
   `camera.near/far`（防每帧重算投影矩阵）。天空半径不能读那个值，要读本帧算出的那个数：
   在 `tightenClipPlanes` 里无条件补一行 `camera.userData.clipFar = far`，`Stars` 读它。
   **理由不是「怕被远平面裁掉」，是「星点会画到天体前面」**——见 5。

5. **深度关系：天空必须始终在最远天体的表面之外。** `farFloorFor` 的口径是
   `1.2 × max(到各天体球心的距离 + 4R)`，而天空在 `far / 1.2`，两个 1.2 互相抵消，
   所以 **天空半径 ≥ 最远天体球心距离 + 4R**，也就是至少在那个天体表面外 3R。
   贴地取景时最远的通常是太阳：`1.5e11 + 4 × 6.957e8 = 1.528e11`，天空落在太阳表面外 3R，
   不是「太阳球体内部」。
   读滞后值的后果要算清楚：`camera.far` 的写回滞后是 5%，在贴地取景的 1.83e11 上是 9.2e9 m，
   而 3R 只有 2.1e9 m——**5% 的滞后足以把天球从「太阳外 3R」缩到「太阳球体里面」**。
   那时加法混合的星点会透过日面画出来（不是被裁掉），这才是必须无条件写 `clipFar` 的原因。

6. **亮度判据沿用沙盘口径。** 边缘 12 块均值 ≥ 2 × 8.94 = 17.88 且 ≤ 4 × 8.94 = 35.74
   （上限就是 `SKY_MAX_RATIO = 4`）。沙盘实测 18.56，实境到位后同口径应落在 18–19；
   比 17.88 低就是层没挂上或强度掉了。

7. **挂载开关要独立，定义点有三处。** `decor` 同时管星空、小行星带、尾迹，而实境要星空、
   不要那两样（尾迹记世界坐标 ~1.5e11 m 且 `frustumCulled = false`，会把亮斑甩到屏幕任意位置）。
   新增 `SystemLook.sky`，必填、无默认值。三处定义点：

   | # | 文件 | 位置 | 值 | 说明 |
   | --- | --- | --- | --- | --- |
   | 1 | `src/solar/systems.ts` | `REAL_PROTO.look` | `sky: false` | `?proto=1` 测量夹具必须保持空背景 |
   | 2 | `src/solar/systems.ts` | `REAL_SYSTEM.look` | `sky: true` **显式写** | 现在写的是 `{ ...REAL_PROTO.look, orbitLines: true }`，spread 让 `tsc` 不报，会静默继承 `sky: false`，实境照样黑——这一处是本次修复新增的第三点 |
   | 3 | `src/solar/system-context.tsx` | 沙盘 `SOL_SYSTEM.look` | `sky: true` | 沙盘现在靠 `decor: true` 挂星空，换成 `sky` 之后 `decor` 只管小行星带与尾迹 |

   第 1、2 处在渲染位写作用域（`systems.ts`）；第 3 处不在，1.4.0 动工时按任务卡指派。
   挂载条件从 `look.decor` 改成 `look.sky`，`decor` 只留 `Asteroids` 与 `Trails`。

8. **探针。** 三条，缺一条这个决策就只能人眼判：

   - `__solarLook().mounted` 现在只有 `{ clouds, belt }`，加 `stars: 0 | 1`；实境必须读到
     **`mounted.stars === 1`**，夹具必须读到 `0`。
   - 新增 `__solarSky()`，返回 `{ radius, near, far, clipFar, scale }` 五个值，
     **三个距离必须分开返回**：`near` / `far` 是相机当前生效的裁剪面（`far` 就是 `camera.far`），
     `clipFar` 是本帧算出来的那个数（`camera.userData.clipFar`），`radius` 是天空实际半径。
   - 断言用 **`camera.far`** 这一支：`near < radius < camera.far` 且 `radius / camera.far ∈ [0.82, 0.85]`
     （理论 0.8333）。**这条要能在 5% 写回滞后时红**——一旦有人把天空半径改回读 `camera.far`，
     在快速缩放的帧上 `radius` 会短暂接近或越过 `camera.far`，这条就红；
     同时 `clipFar ≠ far`（滞后差 > 1%）也要能读到，作为佐证。
   - **绝对深度断言（抓 `farFloorFor` 的 pad 改动）：** `radius ≥ max_i(到天体 i 球心的距离 + 4 R_i)`，
     取遍当前可见集合；最弱的一条兜底是 `radius ≥ 到太阳球心的距离 + R_sun`（R_sun = 6.957e8）。
     这条专抓「有人把 pad 从 1.2 调小」：pad 改成 1.05 时 `farFloor = 1.05 × max(d + 4R)`，
     而 `radius = far / 1.2 ≥ farFloor / 1.2 = 0.875 × max(d + 4R)`，比左边的阈值小 12.5%，必红。
     它同时把 §2.5 那条「天空永远在最远天体表面外 3R」从文字变成可判的数。

**推翻条件：** 谁把天空半径改回读 `camera.far` 或任何滞后值，先量「天空半径是否仍大于所有天体的
远表面距离」。量不成立就退回 `clipFar`；量成立（滞后从未超过 3R 的余量）才可以放松，并且要在
本文补一行动态余量的证据。

## 3 决策 2 飞行：选目标 → 推进 → 到达

**结论：** 选街机档，`v = max(视距 / 12, 1e4 m/s)`，**视距 = 相机到当前目标天体球心的距离**。
「飞」的动词是三拍：**选目标（不瞬移）→ 按住推进 → 到达 1.2R 停**。
本轮不做 6DoF，不做自由姿态；跨天体靠飞行，不靠跳。
30.3 s 那个数作废（它混用了两个目标），正确值见 3.3。

**数字：**

### 3.1 输入与状态机

| 输入 | 动作 | 改什么 | 约束 |
| --- | --- | --- | --- |
| 单击取景按钮（地球 / 月球 / 冥王星…） | **选目标** | 只改 `目标`，相机不动；视距 = 相机到该天体球心的**当前**距离 | 不瞬移。现有「点一下跳过去」的行为改成双击，见下行 |
| 双击取景按钮 | 瞬移到该天体的取景位（`body.focus`） | 视距 = `focus` | 保留熟手路径，但**不是验收路径**；瞬移不计时 |
| 按住推进键（W / ↑ / 屏幕推进键） | **推进** | 视距按 `v` 收缩 | 松手即停；到 `1.2 R` 钳住并报「到达」 |
| 按住后退键（S / ↓） | 后退 | 视距按同一 `v` 扩张 | **不新增距离上限**：米制相机现在没有上限，这次也不造一个；沙盘的 `MAX_DISTANCE`（280，世界单位）不适用于米制，别拿它当米制的天花板 |
| 滚轮 / 双指 | 改视距**目标** | 对数目标 + 一阶跟随（复用 `ZOOM_NOTCH_LOG`、`ZOOM_TAU`、`ZOOM_STEP_MAX_LOG`） | **仲裁只有一条：按住推进期间滚轮不生效；松手后把滚轮目标重置为当前视距。** 不要「取大」「取小」这类没说清的说法 |
| 换目标 | 速度**不清零** | 新的 `v = 新视距 / 12`，下一帧生效 | 滚轮的「目标视距」清零，避免跨目标残留 |

- **wide 不是飞行目标。** 地月中点是个空点，速度在空点会归零，永远飞不到月球。
  wide 只用于观察与连续缩放；在 wide 下按推进键，目标自动取**地球**，HUD 显示「目标：地球」。
  （旧稿在这里写过「扩张到 4e13 为止」。全仓搜过，没有值为 4e13 m 的常量——只在旧稿里出现过一次，
  所以「复用现有常量」这条落不了地，按它的意图改成不设上限，见上表后退那一行。）
- 四个取景按钮（地月同框 / 地球 / 月球 / 冥王星）里，**只有后三个是飞行目标**。
- 到达判据：`视距 ≤ 1.2 R × 1.005`；到达后视距不再收缩，但后退键立刻可用。

### 3.2 用时公式

`t = 12 × ln(起点距离 / 终点距离)`，终点 = `1.2 R`。这是 `v = 视距 / 12` 的解析积分：
`d(t) = d₀ e^(−t/12)`。地板 1e4 m/s 只在视距 < 1.2e5 m 时起作用，而所有终点都 ≥ 1.426e6 m，
所以本版用不到地板。

### 3.3 用时表：起点实测，验收现算

**验收不读这张表的起点。** 按下推进的那一刻读 `__solarFlight().dist` 当起点，
判 `|lastMs − 12·ln(起点 / 1.2R)| / 期望 ≤ 10%`——起点随历元变（月相 + 月球偏心率 e = 0.0549），
写死在表里第二天就不对了。表只留三件事：当前历元长什么样、相带有多宽、公式对不对。

实测（快照 `runs/snapshot-t30-20261025-193620/`，1280×720，进实境后 `realFocus = wide`）：

| 目标 | 起点（相机到球心，实测） | 终点（1.2 R） | 用时（τ = 12 s） | 备注 |
| --- | --- | --- | --- | --- |
| 地球 | 8.678e8 m | 7.6452e6 m | 56.78 s | 相带 48.4–57.4 s |
| 月球 | 5.259e8 m | 2.08488e6 m | 66.36 s | 相带 64.0–73.0 s |
| 冥王星 | 4.632e12 m | 1.42596e6 m | 179.92 s | 随历元漂，量级不变 |

- **相带怎么来的。** `frameEarthMoon` 把相机放在「地月中点 + 日向 × 1.75 × sep」，所以相机到两颗天体的
  距离都落在 `[1.75·sep − sep/2, 1.75·sep + sep/2]` 里。`sep` 自己随月相与月球偏心率在
  `3.633e8`–`4.055e8` 之间，于是这个距离带是 **4.330e8–9.124e8 m**，折成时间：
  地球 48.4–57.4 s，月球 **64.0–73.0 s**，往返 **128.1–146.0 s**。
  迭代一次就够：`sep` 的 ±5.5% 传到时间上是 ±0.6 s，不影响结论。
- **当前历元落点。** 快照里 `distTarget = 6.899e8`（到地月中点）、月球在 `5.259e8`（偏近侧）、
  地球在 `8.678e8`（偏远侧）。这一天两条都在相带的内侧，不是极值。
- **验收用哪一行：** 不用行。用现算：`期望 = 12 × ln(起点 / 1.2R)`，起点由探针给。
  相带只用来判「探针读到的起点有没有离谱」（落在 4.330e8–9.124e8 之外就是取景逻辑坏了）。
- **对照（不是玩家路径）：** 真实 delta-v 恒速 1.09 km/s，地月往返 8.14 日；
  地球→灶神星（Hohmann，Δv ≈ 10 km/s）1.09 年；到 1e16 m 要 29 万年。
  这三条进 CHANGELOG 的取舍说明，不进验收。
- **量级参照：** 从地月同框（视距 6.899e8）一路倒退到 1e16 m，按同一个 τ 是
  `12 × ln(1e16 / 6.899e8) = 197.9 s`。不是飞到某个天体，只作量级参照。

### 3.4 采集方法与探针

- 计时由**页面自己打点**，不用人眼掐表：按下推进键记录 `performance.now()`，到达判据满足时再记一次；
  差值写进 `__solarFlight()` 的 `lastMs`。
- 探针（新增 `__solarFlight()`）：`{ target, dist, lastMs, arrived, speed }`——
  `dist` 是相机到目标球心的距离（米），`speed` 是本帧的 `v`，`arrived` 是布尔。
- **三次跑的复位协议（不写死起点，但起点必须可重复）：** 每次按推进之前，先用后退键回到出发视距
  （或双击该天体按钮回到它的取景位），**读 `__solarFlight().dist` 记下起点**；三次的起点之间
  相对差 ≤ 0.5%，否则本次作废重跑。每次的期望值用当次的起点现算。
- 断言：三次 `lastMs` 的中位数落在 `12 × ln(起点 / 1.2R)` 的 ±10% 内，且 `arrived === true`。
  三次起点不一致时不许取中位数——那是把三个不同的量平均掉了。
- 玩家路径（不吃夹具）：打开实境 → 单击「月球」→ 按住推进 → `arrived` 变真时停表。
  这条进 1.4.0 的验收清单，优先级高于任何夹具推目标的路径。

### 3.5 代价，四条

① 速度是视距的函数，不是独立档位：想慢慢看近地表面，必须先把视距缩到 1e7（那时 v = 8.3e5 m/s）。
② 视距 → 0 时速度 → 0，飞行是渐近的；靠 1e4 m/s 地板兜底，代价是贴脸那一段「变钝」。
③ 与帧率耦合：每帧位移 = `dt / 12`，60 fps 是 0.14% 视距/帧，20 fps 是 0.42%；
`Simulation` 的 `delta = min(raw, 0.1)` 钳住的是最坏情况，不是手感。
④ **单 τ 拉不开尺度差**：指数模型下，地球→冥王星（179.9 s）的用时只是地月（66.4 s）的 2.7 倍，
而距离差 8810 倍（4.632e12 / 5.259e8）。跨行星的「一顿饭之内」满足得很宽松，
代价是**时间不承载距离感**。

**推翻条件：** 观察位若判「跨行星太快、没有距离感」，单 τ 救不了——必须让 τ 随距离增长
（例如 `τ = 12 × (1 + 0.5 × log10(d / 1e9))`，地月仍 ~66 s，冥王星那趟拉到 ~10 分钟）。
另一个推翻点是 1.5.0 给实境打开时间推进（`freezesTime: false`）：那时真实 delta-v 有了玩法用途
（等哈雷回归、等某次凌日），要改成「真实档为默认 + 街机档为可切 warp」。

## 4 决策 3 连续缩放验收

**结论：** 抖动阈值 **0.35 px**（p10–p90，120 帧，像素回读），与 `proto-jitter` 的
`MODERN_PP_MAX` 同一套量法与同一个闸；帧率下限 30 fps（p95 ≤ 33.3 ms，单帧 ≤ 100 ms），
只在 Intel Arc 130T 真机上量，抖动在 SwiftShader 夹具上量。
验收路径 1e13 → 1.2 R = 7.645e6 m，6.12 个量级。

**数字：**

1. **同一个量只有一个阈值：0.35 px。** 旧稿把两套数混着用了——量法抄 `proto-jitter`
   （像素回读圆盘左右缘中点、120 帧 p10–p90），阈值却拿 `follow-jitter` 的 0.5 px。
   这两条测的不是一个量（`follow-jitter` 跟的是沙盘目标，`proto-jitter` 跟的是米制地球圆盘），
   不能互换。本决策与 `proto-jitter` 同一个量（米制地球圆盘的像素回读），所以用同一个 0.35 px。
   **三个比值各自的视口必须标清楚，别把 1920 的底拿去给 1280 的验收背书：**

   | 比值 | 视口 | 夹具点 | 噪声底 | 倍数 |
   | --- | --- | --- | --- | --- |
   | **10 ×** | **1280×720（验收视口）** | dist=1.2e7 | **0.035** | **0.35 / 0.035 = 10.0** |
   | 5.2 × | 1920×1080（`proto-jitter` 视口） | dist=1.2e7 | 0.067 | 0.35 / 0.067 = 5.2 |
   | 4.3 × | 1920×1080 | dist=1.2e7 | 0.081（旧注释） | 0.35 / 0.081 = 4.3 |
   | 0.85 × | 1920×1080 | dist=**1.8e7** | 0.410 | 0.35 / 0.410 = 0.85（会红） |

   本版验收在 **1280×720** 上跑，所以生效的是第一行那个 **10 倍**；5.2 与 4.3 是 1920 的对照，
   只说明「同一条阈值在 1920 上也留了 5 倍」；0.85 是反例，证明夹具点一挪就会红。
   旧稿写的「0.5 px 是噪声底 6.2 倍」作废。

2. **抖动只在标定点上量，其余取样点只判结构。** 圆盘半径 ≥ 30 px 才有左右缘可读，
   对应视距 ≤ 2e8 m（`radiusPx = focal × tan(asin(R/d))`，focal 937.83 @ 42°/720 行）。
   **6 个抖动取样点全部钉在 `dist = 1.2e7`**（1280×720 的实测标定点），每个点独立停稳、
   独立采 120 帧——不是 6 个不同视距各采一次，因为 t15 已经证明底随夹具点变（1.8e7 那档是 0.410）。
   缩放路径本身走 24 个对数等距取样点（1e13 → 7.645e6，每 0.266 个量级一跳），这 24 个点
   **只判结构**：`near < 天空半径 < camera.far`、天体投影不跳、天空层亮度在预算内。
   抖动量级与缩放路径的量级是两件事，别混成一条判据。

3. **每个取样点先停稳再采 120 帧。** 夹具把视距目标推到位后，等到
   `|log 当前视距 − log 目标视距| < ZOOM_SETTLE_LOG`（= 1e-3）并且连续 60 帧不变，
   才开始采 120 帧。没停稳就采，量到的是跟随器的尾巴，不是抖动。
   **取样点之间的连续性不靠抖动判**——由本节第 4 条（log 单调 + 单帧步长）判，两件事别混。

4. **连续性两条判据。** ① 24 个取样点的 log 视距严格单调不增；② 任何一帧的
   `|Δlog 视距| ≤ ZOOM_STEP_MAX_LOG`（= 0.125）。第一条防「来回抖」，第二条防「一帧跳过去」。

5. **6.12 个量级与沙盘预算差 4 倍。** 沙盘的缩放预算 `ZOOM_STEP_BUDGET = 15` 格，一格
   `ZOOM_NOTCH_LOG = 0.147` 个自然对数（≈0.064 个量级，连滚最多 2.2 倍）；实测 11 格从总览
   走到太阳 3R，约 1.0 个量级。实境 1e13 → 7.645e6 是 14.08 个自然对数：按一格 0.147 算是 96 格，
   连滚加速后 44 格。所以**玩家不是一次连续缩放走完**：取景按钮负责跨量级跳，
   每段连续缩放 ≤ 3 个量级；验收夹具直接推视距目标，在 `ZOOM_REF_RATE = 4.5` log/s 下是 3.1 s。

6. **帧率：120 帧窗口，连跑 2 次取较差。** 判据 `p95 ≤ 33.3 ms` 且 `maxFrame ≤ 100 ms`；
   两次跑取更差的那次进结论。产物按 `runs/fps-1.4.0-<ISO>.json` 落盘，字段
   `{ gpu, driver, resolution, dpr, tier, p50, p95, maxFrame, windowFrames, runs }`——
   真机型号与分辨率必须写进产物，否则半年后没人知道这个数是哪台机器上的。
   **这条不进 `verify.mjs`**：verify 跑的是 SwiftShader 软件光栅，帧率在它上面只能反映 CPU 频率，
   所以帧率只做真机验收记录（`docs/` 里存指针，不存结论）。
   为什么闸是 33.3 ms 不是 26 ms：`quality.ts` 的降档触发是 `downP95Ms = 26`，验收闸必须比降档闸宽，
   26–33.3 ms 这一段是有意留的灰区（产品会自己降一档，验收仍算过）。

7. **量在哪台设备：** 帧率在 Intel Arc 130T（Core Ultra 5 225H，驱动 32.0.101.6554，
   Edge，1280×720 CSS、dpr 上限 1.6 → 2048×1152 设备像素，`?tier=2` 钉住档位）上量；
   抖动在 SwiftShader 夹具上量（`--use-angle=swiftshader`，1280×720）。
   分工的理由：抖动是量化误差，与光栅器无关，夹具可复现；帧率是填充率，软件光栅比真机慢 5–20 倍。
   掉到 30 fps 以下的降级杠杆是 dpr：1.6 → 1.28 是 2.36 MP → 1.51 MP（−36%）。

8. **噪声底是夹具点专用常数，验收必须在标定点上量。** t15 实测（同一 build、**1920×1080**、
   只改 `?dist=`）：`dist=1.2e7` 底 0.067，`dist=1.8e7` 底 0.410（6.1 倍），
   `dist=2.4e7` 底 0.082——不单调，不能插值。`dist=1.2e7` 是反解出来的标定点
   （圆盘左右缘刚好在画面内、f/视距 最大），**不许为了取景好看改它**。
   在 1.8e7 那档，0.35 px 只剩 0.85 倍余量——直接红。1280×720 的标定点同样是 1.2e7（底 0.035）。

9. **最近视距 1.2 R，不往下探。** 1.2 R = 7.645e6 m（1274 km 高度），复用 `MIN_DISTANCE_RADIUS_FACTOR`。
   再往下到 R + 2 km 时 near 降到 1.556 km、far 仍在 1.8e11（太阳），深度跨度 1.16e8:1，
   比 2^24 预算大 6.9 倍，云壳（1.02 R）在轮廓处与地表视线距离趋近 0，会出 z-fight。那一段是 1.8.0 的活。

**推翻条件：** 0.35 px 是在**空背景**上量的，1.4.0 的实境多了一层加法混合星空；如果边缘掩膜把星点
算进圆盘，噪声底会抬上去。判据：`?proto=1&still=1` 的噪声底一旦超过 0.07 px，
0.35 px 就只剩 5 倍余量，必须按「新噪声底 × 5」重定。另：换夹具点（视距、细分、视口）
或换光栅器（真机 / SwiftShader）都要重测，t15 已经证明这个量不是几何的平滑函数。

## 5 决策 4 冥王星与哈雷

**结论：** 冥王星进入**飞行目标列表**（不是「第三个取景按钮」），`focus` 从 1.5e9 改到 1.2e7；
**哈雷从 `REAL_SYSTEM_BODIES` 摘掉**（`HALLEY_ELEMENTS` 与 `marker` 字段留在数据层，
1.5.0 的「1986 哈雷回归」再接）。

**数字：**

1. **冥王星现在等于没有。** `radius = 1.1883e6`、`focus = 1.5e9`，圆盘半径
   `937.83 × tan(asin(1.1883e6 / 1.5e9)) = 0.74 px`。按钮按下去看到的是一个 1.5 px 的点，
   和一颗亮星分不出来。要 100 px 半径得 `d = 1.114e7`；取 1.2e7 给 93.3 px，留一点余量。

2. **哈雷在任何视距下都不是像素。** `radius = 5.5e3`，`focus = 5e8` 下 0.0103 px；
   贴到 1.03e5 m（离核 103 km）也只有 50 px 半径。它在数据里存在的形式是
   `marker: { size: 6 }` 的 UI 点，「看见哈雷」与米制量纲无关，1.4.0 的星空层与缩放验收对它零贡献。

3. **摘哈雷省下的验收面是 3 条。** 少一条天体、少一条轨道线样本（i = 162.19° 的逆行轨道，
   是三条轨道线里唯一的逆行样本）、少一个 marker 渲染路径（`NucleusMarker`）。

4. **改 `focus` 有三个消费者，必须一次改完。** 相机取景距离、贴图预算预判
   （`focus = 1.5e9` 时 plan 出来 2.4 px，改 1.2e7 之后 298 px @dpr1.6）、
   标签最大可见深度 `max(focus × 48, radius × 200)`：7.2e10 → 5.76e8。

5. **探针（这一条以前只能人眼，本次补上）：**
   - `__solarFocus()` 新增，返回 `{ target, dist, radiusPx, labelMaxDepth }`；
     `radiusPx` 用与拾取器同源的 `focal × tan(asin(R/d))`。
   - 断言三连：**双击冥王星（瞬移到 focus 1.2e7）之后**读探针，判 ① `radiusPx = 93.3 ± 5%`
     （即 88.6–98.0）；② `__solarTextures().items` 里 `pluto` 的 `width ≥ 256`（`textureReport()`
     报的是落地尺寸，plan 的期望值 298 px 见第 4 条，落地按档位取整，所以判 ≥ 256 而不是判 298）；
     ③ `labelMaxDepth = max(1.2e7 × 48, 1.1883e6 × 200) = 5.76e8`。
   - 这三条都在**玩家路径**上判（双击按钮 → 等一次贴图 plan 完成 → 读探针），不要夹具注入。
     单击只选目标不瞬移，视距是当前距离，贴图 plan 不会按 1.2e7 排——所以这里必须是双击。

6. **冥王星是 1.4.0 的尺度右边界。** 39.59 AU = 5.92e12 m 到地月 6.7e8 m 是 3.95 个量级，
   正好把「1e7 → 1e13」这条相机路径的两端都占住；1.6.0 的 AU → 光年换算从这里起。

**推翻条件：** 如果 1.5.0 把「真实事件玩法（1986 哈雷回归）」提到主带之前，哈雷的 marker 会先成为
玩法目标，那时改成「摘冥王星、留哈雷」。两个都留不成立：5 个天体全留意味着多两条没有飞行路径的天体、
一条极端轨道线、一个没有屏幕尺寸规则的 marker，三项都要补断言。

## 6 范围：跟 PLAN 对齐

PLAN §2 的 1.4.0 进项是「记录 + 光照只到晨昏线」。本规格照 PLAN 写，不反过来：
**旧版 §6 把落点记录划出 1.4.0 的那一段作废**（队长裁决：保记录、砍光照）。

- **落点记录在 1.4.0**（数据结构 + 卡片一行），本规格不实现它，但要给判据，免得实现位自己定：
  - 触发：相机到某天体球心 ≤ `8 R` 且**连续停留 ≥ 5 s**（实境时间冻结，按墙钟算），
    自动生成一条记录，**无确认键**。
  - 去重：每个 `body.id` 一次会话只记一条；离开后再回来不重复记。
  - 探针：`__solarVisits()` 返回 `[{ id, wallMs }]`；玩家路径断言——
    **双击地球停 5 s、双击月球停 5 s**，长度为 2（双击 = 瞬移到取景位，视距进 8R 内；单击不瞬移，
    视距还停在 wide 的 6.899e8，离 8R = 5.1e7 差一个量级，不会触发）。
    另一种写法是「飞到 ≤ 8R 后停留」，两条只能选一条；本规格选双击，因为它在验收里可一步复现。
- **光照到晨昏线为止，并给一个数。** 夜灯、镜面、法线贴图挪到 1.5.0。1.4.0 的判据：
  在晨昏线两侧各取一块 24×24 像素（沿日下点 → 反日点方向各偏 30°），**亮侧 / 暗侧 luma 比 ≥ 1.5**。
  为什么是 1.5：夜面片元着色器的 shade 地板是 0.08，日下点是 1.0，理论比值上限 12.5；
  1.5 只要求「能看出昼夜」，不要求夜景，与「砍光照到晨昏线」的裁决一致。
  采集方法与 `eclipse-hemisphere` 同一套（像素回读、整盘平均），采样点用 `__solarPlace` 摆位。
- **进实境的默认机位：不做「先落地球近地」，保持 wide。** 理由是一个数：入口若落在 1.2 R，
  地球圆盘半径 1407 px，而画面只有 720 行——第一帧整幅都是地球表面，**星空层在入口完全不可见**，
  而星空是 1.4.0 的头号交付；同时 5 s 后 §6 会立刻生成一条地球落点记录，「还没飞就到一个落点」。
  玩家读第一条说的「第一眼不能是黑」，由决策 1 直接解决：wide 入口的亮度从 8.94 抬到 18–19。
  推翻条件：观察位在 1.4.0 落地后仍判「第一眼是空的」，改成入口 3 R（圆盘半径 331.6 px，
  四角还留着星空），**不要用 1.2 R**。
- 主带、星图、发现机制、奥尔特云、地表不在 1.4.0。
- HANDOFF 提案 1（短时基准定画质档）按 PLAN 归验证位，本规格只提供「帧率在哪台设备量」这一条口径。

## 7 这份规格里哪个数最可能被现实推翻

**月相那条带的下界 64.0 s。** 它靠三个假设：相机在日向一侧（`frameEarthMoon` 的 `dir`）、
相机到中点的距离就是 `1.75 × sep`、以及 `sep` 的范围是 `a(1±e)`（a = 3.84399e8、e = 0.0549）。
1.4.0 若改 `frameEarthMoon` 的 1.75 这个系数，整条带跟着平移（1.75 → 1.5 时下界掉到约 50 s）。
如果它掉了，不是改阈值，是把验收从「相带内」换成「用当次 `__solarFlight().dist` 现算的期望值」——
判据跟着探针走，不跟着常数走。这一条本来就是这么写的，改动只是把「现算」从备选提到主路径。

第二个是 0.35 px 的 10 倍余量（1280×720、dist=1.2e7、底 0.035）：它是在空背景上量的，
1.4.0 加了星空层之后要重测（见 §4 推翻条件）。

## 8 检查脚本：验内部自洽，不验前提

`node scripts/check-spec-1.4.mjs` 读本文件，四类判据：

1. **结构**：四个决策段都在，每段有 `**结论：**`、数字、`**推翻条件：**` 三样；禁词表命中即红。
2. **数字在场**：每段的必填数字逐条命中，清单在脚本的 `DECISIONS` 表里。
3. **算术复算**：脚本自己解析 §3.3 的用时表，按 `t = 12 × ln(起点 / 终点)` 逐行重算（1% 容差）；
   再核 `往返 = 2 × 单程`（从相带那一行现算）、冥王星 `93.3 px` 的三角公式、
   `5.76e8 = max(1.2e7 × 48, 1.1883e6 × 200)`、`0.35 / 0.035 = 10` 这三个比值，
   以及**相带能不能从 `frameEarthMoon` 的三个参数（1.75、a、e）推出来**。
4. **来源声明**：文首必须有「数值来源」与「行号基准」两行，否则人工复核无从下手。

**这个脚本验的是「公式与表一致、前提能推得出来」，不验「前提对不对」。**
算术复算抓得住「表里写 66.36 s 而公式给 72.29 s」这种自相矛盾；
它抓不住「a、e、1.75 这三个前提本身过期了」。后者只能靠下面这张人工复核项清单去核：

| 人工复核项 | 值 | 来源 | 什么时候要重核 |
| --- | --- | --- | --- |
| wide 起点距离（地球/月球/冥王星） | 8.678e8 / 5.259e8 / 4.632e12 m | 快照 `runs/snapshot-t30-20261025-193620/`，`__solarCamera().pos` + `__solarKepler()` | 换历元、改 `frameEarthMoon`、改月球根数 |
| 1280×720 噪声底 @dist=1.2e7 | 0.035 px | t15 `.tmp-t15-radius.json` | 换 build、换视口、换夹具点 |
| 抖动阈值 | 0.35 px | `verify.mjs` 的 `MODERN_PP_MAX` | `proto-jitter` 改闸 |
| 帧率闸 | p95 ≤ 33.3 ms / 单帧 ≤ 100 ms | 本规格 §4，比 `quality.ts` 的 26 ms 宽一档 | `quality.ts` 改降档闸 |
| 冥王星 focus | 1.2e7 m | 本规格 §5（100 px 反解得 1.114e7） | 改冥王星半径或取景口径 |

脚本能现算的都现算了（表内用时、往返、圆盘半径、标签深度、比值）；剩下这五行算不了，

`--selftest` 造四份反例：删一段、只在段内抽掉一个数、插一个禁词、**把某个用时改回 30.3**
（最后这条专门验算术复算有没有真在跑）。四份都红、原文绿，才算检查器能红。
