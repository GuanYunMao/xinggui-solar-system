# 1.3.4 收口前玩家判读：三条门是观测还是等待

> 判读者：观察位。依据是代码（`observe.ts` 的三条判据、`store.ts` 的累计与清零、`Hud.tsx` 的芯片行）+ 机制位给的实测数（月食 7.54 实秒一轮、每轮 0.75 秒；水星一圈 20.8 实秒）。
> 屏幕尺寸是我按 home 机位（`[0,40,112]`，视距 118.9 wu，fov 42°、720 行 ⇒ 焦距 937.8 px）算的，不是量的；天体在轨道上远近浮动，数只保证量级。
> 没有真机试玩。凡「他会在第几秒点别处」这类判断是预测，不是实测。行号核于 2026-10-25 19:36 工作树（HEAD `9304a99`）。
> 文案取工作树未提交版本（`git diff src/solar/ModeBadge.tsx`）：time「月球进影子时，它正被选中」、target「选中水星，看它绕满一圈」、layer「没有名称与轨道，还选得中行星」。若收口前再改，§1/§3/§4 按新文案复核。

## 0 一句话

三条门里，一条是观测（time，0.75 秒的现象），一条是等待（target，20.8 秒的不可见计时器），一条是 HUD 点击（layer，芯片行把名字都印着）。三条都能只靠 HUD 完成，没有一条必须看画面。

## 1 门·target：那 20.8 秒是等待，不是观测

**结论**：这 20.8 秒里玩家在等一个看不见的计时器。画面在动，但没有一处告诉他「这是第几圈、还剩几秒」，也没有一处告诉他「刚才那次点击把进度清零了」。

**依据**：

- **选中即飞过去。** 点水星芯片，相机用约 0.95 秒飞到 `focus = 2.8` wu（`data.ts:141`），水星盘面直径约 **257 px**，占屏幕高度的三分之一。玩家看到的是「一颗灰色大球」，不是「一个轨道上的点」。
- **提示许诺的「绕满一圈」，默认机位看不到。** 现在的文案是「选中水星，看它绕满一圈」。可选中之后相机贴在 2.8 wu 上看球，可视宽度约 2.15 wu，轨道半径 8.6 wu——整条轨道在画面外，只有穿过水星附近的一小段线。真要看它绕，得自己把镜头缩出去（滚轮一缩，选中还在，计时不清零）。提示没说这一步。
- **画面确实在动，但动的不是「一圈」。** 相机跟随时只做平移、朝向不变（`SolarCanvas.tsx:3076-3082`），所以水星绕太阳一圈的过程中，它相对太阳的亮面会走完一次「满 → 黑 → 满」；自转 `spin 0.12` × 8.2 模拟秒 ≈ **56°**（`data.ts:139`）。这是贴脸机位下唯一的「一圈」证据，没有刻度、没有起点标记，中途那段全黑还会被读成「球灭了」。
- **计时器在屏幕上不存在。** `mercuryWatchSeconds` 只出现在 store 内部（`store.ts:216/377/464/471/475`），`Hud.tsx` 和 `ModeBadge.tsx` 一次都没读过它；门面板只有 0/3 的总进度（`ModeBadge.tsx:220-240`）。玩家没有任何办法知道「还剩 12 秒」。
- **任何一次选中都清零，包括再点一次水星。** `store.ts:427-431` 两个分支都写 `mercuryWatchSeconds: 0`。所以「换目标归零」这条口径实际更宽：再点同一颗、点一下别的行星看卡片、点月球去试时间门，全部从头再来。
- **速度是持久化的，门的真实时长跟着变。** `DEFAULT_SPEED = 8`（`store.ts:103`），8× 下 20.8 秒；读档会恢复上次速度（`store.ts:597`），1× 是 **166 秒**，0.05× 是 **3330 秒**（55 分钟）。门判的是模拟时间（`observe.ts:321-344`），提示里一个字都没提速度。
- **门亮的瞬间没有现象，连「回到满圆」都差一截。** 计时从选中那一刻算（8.2 模拟秒），但相机飞行的那 0.95 秒里水星已经走了 0.375 模拟秒，相位「满」要等到约 8.575 模拟秒。所以门在 8.2 亮，球在 8.575 才回到满——**差约 0.95 实秒**。屏幕上唯一的自然书签和门亮不是同一帧。

**替代方案与代价**：

- **A 改写提示**：现在是「选中水星，看它绕满一圈」，缺三样——8× 前提、约 21 秒的量级、以及「要不要把镜头缩出去才看得见一圈」。加一句「8× 下约 21 秒，缩出去能看见整条轨道」。代价：文案变长，且把「要等」明说了；好处是不用改一行代码。
- **B 加进度读数**：门面板显示「已观察 12.3 / 20.8 秒」。代价：等于承认这是进度条，和「观测」的说法自相矛盾；但它是诚实的。
- **C 降门槛**：从「满一圈」降到「亮面由满走到半」，8× 下约 **5.2 秒**。代价：判据要读相机—天体—太阳的夹角，属渲染域（1.4.0 的活），1.3.4 收口前做不完；不改判据只把阈值改成四分之一圈的话，仍然是计时器，只是短了。
- **D 删掉这条门**：`GATE_REQUIRED` 3 → 2，槽位表与 schema 刚收到 3 又要再动一次，短码版本还得再升。代价最大，不推荐。

**这一版该删什么**：删掉「静默清零」——再点同一颗水星不清零，只有换到别的天体才归零；顺手把提示改成 A。这两件都不动判据，成本是两行代码加一条文案。如果只准删一件，删静默清零：它让玩家永远学不到「刚才快成了」。

## 2 门·time：0.75 秒的现象，7.54 秒的等待——这条是观测，但窗口很薄

**结论**：这条是真观测：有一个玩家能看见的现象（月球变暗），有一个自然周期（7.54 秒），门亮的时刻和现象是同一帧。麻烦在于现象只持续 0.75 秒，而且门在相机还在飞的时候就可能亮。

**依据**：

- 选中月球，相机飞到 `focus = 1.7` wu（`data.ts:230`），月球盘面直径约 **222 px**。位置在 `observe.ts` 的 `sandboxEclipse`：月食每 **2.971 模拟秒**一轮（8× ⇒ 7.54 实秒），进入段 0.294 模拟秒（8× ⇒ **0.75 实秒**）。等待占 90%，现象占 10%。
- 判据只看「进入那一帧月球被选中」（`timeGateWitnessed`，`observe.ts:297-304`）。选中在点击的瞬间就写进 store（`store.ts:428`），而相机飞过去要 0.95 秒——如果进入发生在飞行途中，门会亮，玩家还没看到月球。这是「灯先亮、现象后到」。
- 判据不检查玩家在不在看（`observe.ts:291-293` 自己写着这一条）：切到别的窗口、低头看卡片，门照样亮。所以它是「选中 + 等」的驻留判定，和 target 同构；区别只在于它等的是一个有现象的时刻。
- 速度依赖同样存在：1× 下月食周期 **60.3 秒**，0.05× 下 **1206 秒**（20 分钟）。提示没写速度。

**替代方案与代价**：把「进入那一帧被选中」放宽成「进入前后 ±1 秒内被选中过」，代价是判据变松、可被「先点月球再乱点」蹭到；收益是飞行途中的那次也能算。或者不改判据，只把提示写成「把速度调到 8×，等月球变暗」，代价是提示开始指挥操作，与「只描述现象」的规矩冲突。

**这一版该删什么**：不需要删门，删「提示不提速度」这个坑——在提示里给一句「8× 下约 7 秒一轮」。一句话，不改判据。

## 3 门·layer：关掉名称和轨道之后，一眼认得出的只有三颗，而 HUD 把答案印着

**结论**：这条是「点得中谁」，不是「认得出谁」。现行文案已经改成「没有名称与轨道，还选得中行星」——它比旧文案诚实，但前提不成立：芯片行把每一颗的名字印在屏幕顶上，点芯片也算数。真要按画面认，地球 12 px、木星 36 px、土星 30 px 带环，火星 8 px 靠红色勉强算半个，其余都是 6–11 px 的小点，认不出来。

**依据**：

- 判据只要求「名称与轨道都不在 + 选中的是一颗行星」（`layerGateWitnessed`，`observe.ts:366-375`），不区分这次选中是画布点的还是芯片点的。
- 芯片行是常驻按钮，按钮文本就是 `body.name`（`Hud.tsx:632-646`），点它调用同一个 `select`。所以「关两个开关 → 点地球芯片」一步就过，3D 场景一眼都不用看。文案说「没有名称」，名称只是从画面里挪到了 HUD 里。
- 真看画面的话，按 home 机位算的盘面直径：木星 **35.5 px**、土星 **30.0 px**（外加环）、地球 **12.0 px**、金星 **11.4 px**、火星 **8.2 px**、水星 **6.0 px**；天王星/海王星 10–13 px 量级。能靠颜色认的是地球（蓝）、火星（红）、土星（环）；水星和金星都是灰黄小点，6–11 px，认不出区别。
- 默认 `showTrails = true`（`store.ts:357`），所以「轨道都不在」只是环线不在，每颗行星身后仍有一段尾迹：90 个点 × 0.06 wu ≈ 5.4 wu（`SolarCanvas.tsx:1796/1852`），水星是轨道的 36°、木星 10°。画面里仍有运动提示，和文案说的「轨道都不在」不完全一致。
- 点错没有反馈：点到太阳或卫星不算（`observe.ts:360-362`），但界面不告诉你为什么不算。太阳是画面里最大的东西，第一次点它几乎必然。

**替代方案与代价**：

- **A 只认画布选中**：给 `select` 加一个来源字段（芯片 / 画布），门只认画布。代价：一个 store 字段 + 三个调用点 + 一条断言；画布上水星 6 px 难点，但地球 12 px、木星 36 px 够用，门只要求任意行星。
- **B 关标签时把芯片行的名字也隐掉**：不行。芯片行是选卫星的唯一入口（`Hud.tsx:663-677`），隐了名字，卫星没法选，时间门也进不去。
- **C 只把话说圆**：文案改成「画面上没有名称与轨道，还选得中行星」。代价：诚实，但这条门就退化成「关两个开关再点一下」，四把尺子的第 1 条（能不能失败）更难过。

**这一版该删什么**：删掉芯片行对这条门的效力（A）。只选一个动作的话，这个比改文案值：文案已经改过一轮，现状是「说法诚实了，判据还是能绕过去」。如果收口前不敢动判据，退一步把「没有名称」改成「画面上没有名称」（C），至少别让文案说假话。

## 4 三条连起来：第一次玩的路径不顺

**结论**：不顺。最短一条路是 **6 次点击/开关 + 28.3 秒等待**（月食 7.54 + 水星 20.8），但玩家不知道目标门在计时，中途任何一次点击都会把它清零；按面板上 1-2-3 的顺序做，第二条之后还要再点一次才能做第三条，那次点击正好清零——只是门已经亮了，看起来没事。

**依据**：

- 最短路径：点地球 → 点月球（2 次）→ 等 ≤7.54 秒 → 点水星（1 次）→ 等 20.8 秒 → 关名称、关轨道（2 次）→ 点一颗行星（1 次）。相机每次飞 0.95 秒，三次飞行 2.85 秒。
- 按 1-2-3 做没问题；但玩家的自然行为是「先试一下每条」。先点水星（提示直接点名「选中水星，看它绕满一圈」）等 8 秒没反应，再点地球去看时间门——清零；再点水星——又清零。两次之后，20.8 秒变得像「这游戏不认我」。
- 三条提示的语气混在一张面板上：time 写现象（「月球进影子时，它正被选中」），target 写操作指令（「选中水星，看它绕满一圈」），layer 写条件（「没有名称与轨道，还选得中行星」）。玩家读到的是三种东西：一个现象、一条命令、一个条件，不是一条路径。
- target 这一句还和它自己的注释打架：`ModeBadge.tsx` 的 COPY 注释写着「不写操作指令动词」，文案却以「选中水星」开头。更要紧的是它把「哪颗一年绕的圈最多」这个判断直接免了——玩家不用想，照做就行；观测那一步被文案替玩家做完了。
- 20.8 秒的等待长过大多数玩家的「看一颗灰球」的耐心。我的预测：第一次做 target，玩家在第 8–12 秒会点一次别的东西（看卡片、试别的门），然后不知道任务已重新开始。

**这一版该删什么**：删掉「面板上的顺序等于操作顺序」这个隐含约定。要么在提示里写清「三条可以任意顺序，但盯着的那条别换目标」，要么把 target 的累计改成「不清零，只记最高」——后者更贵，但玩家怎么点都不会白等。只选一个的话，删静默清零，理由同上：它是三条门里唯一「玩家做对了却不知道自己错了」的地方。

## 5 汇总：这一版该删什么（按性价比排）

1. **删 target 的静默清零**（`store.ts:427-431`）。成本：两行 + 一条断言；收益：玩家再点同一颗不会白等 20.8 秒。代价：换目标仍然清零，语义没变。
2. **删「面板顺序 = 操作顺序」的隐含约定**：提示里加半句「三条可任意顺序，盯住的那条别换目标」。成本：一句话；收益：第一次玩的人不用试错。
3. **删 target 提示里的「选中水星」**，换回现象描述（例如「一年绕太阳最多圈的那颗，看它绕满一圈」）。成本：玩家可能想不出是哪颗，需要试；收益：这条门从「照做」回到「发现」。代价写在明处：1.3.4 的主题是拆作业感，而「选中水星」这四个字就是作业。
4. **删芯片行对 layer 门的效力**（`select` 加来源字段）。成本：一个字段 + 三个调用点 + 一条断言；收益：这条门真的需要看画面。收口前动不了判据的话，退一步把文案改成「画面上没有名称与轨道」。
5. **删「提示不提速度」**：time 与 target 的时长都随速度档变化（8× 20.8 秒 vs 1× 166 秒），提示里得有一句 8× 的前提。成本：两句话；收益：读档的老玩家不会等 55 分钟。

## 6 什么情况会推翻这份判读

- 如果实测里玩家在 20.8 秒内真的盯着水星看完相位循环、并且门亮时认出了「它回到满圆」，那 target 就是观测，我判错。判据：录屏里有没有一个人在 21 秒里不点击。
- 如果芯片行在关标签时被自动收起（现在没有，`Hud.tsx` 里看不到这条逻辑），layer 的 HUD 捷径不成立，这条判读要改。
- 如果读档速度默认被重置成 8×（现在会恢复上次值，`store.ts:597`），速度依赖那条失效。
- 如果选中不是在点击瞬间写进 store、而要等相机到位（现在是点击即写，`store.ts:428`），「灯先亮、现象后到」那条失效。
