# 验收怎么跑

> **形状判据是门卫，行为判据才是裁判，两层别混成一层报。**
> 形状只证明「这个写法只出现在这里」，行为才证明「它算出来的数是对的」——
> 两层分工见下面「形状判据（`check-shape.mjs`）」。

```bash
npm run build          # 先出 release/（verify 验的是构建产物，不是 dev server）
npm run verify         # = node scripts/verify.mjs（行为验收，跑真浏览器；清单以它的输出为准，本文只解释每条判据验什么）
npm run check          # = 单文件冒烟（起真浏览器，要 Edge）+ 形状判据；前一半 CI 不跑，见「CI 与本地差异」
```

`verify.mjs` 起一个临时静态服务器指向 `release/site`，用系统 Edge（不下载 Chromium）开真浏览器，
软件光栅化（swiftshader）跑 WebGL，把结果打成一坨 JSON，最后一行是结论：

- `"failures": []` + `✓ 全部通过` → 退出码 0
- 任何一条红 → 退出码 1，`failures` 里每条都以 **pass 名 + 冒号** 开头，按前缀就能定位

**`failures` 里只允许出现真回归。** 已知缺陷（真 bug、已定位、还没修）不进 `failures`，
只进 `results` 与一条 `【已知缺陷】` 摘要行——否则基线会被一条修不了的 bug 永久污染，
然后有人开始加 `|| true`。清单与到期条件见「已知缺陷（记录但不判红）」。

`XG_ONLY=mobile,numeric` 只跑指定的 pass（反向验证用）；
**只用于证明那条断言真有牙齿**，常驻验收不带它。

端口默认 4178，被占用会自动往后找（4179、4180…），并打印一行提示。
浏览器路径默认 `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`，
换机器用环境变量 `XG_EDGE` 指过去（`XG_EDGE=/usr/bin/chromium node scripts/verify.mjs`）。
`verify.mjs` / `check-single-file.mjs` / `texture-report.mjs` 读的是**同一个** `XG_EDGE`：一处设，
三处生效，别让某个脚本再长出自己那份硬编码路径（`check-single-file.mjs` 曾经就是，Linux 上直接跑不起来）。
产物目录默认 `release/`，用 `XG_RELEASE` 可以指到一份冻结快照（结构要一致：`site/` + `巡星.html`），
见下节「别和别人的构建撞车」。

### 判据的三类（写断言之前先分类）

分类错了，是两类事故的**共同**来源：**把观测量当判据** → 忙机器上误红，红到没人信
（本仓库真实事故：帧时间写死 `EMA ≤ 26ms`，同一份代码在忙碌机器上 38.7ms / hitch 3，天天红）；
**把结构量当记录** → 整屏黑也全绿（2026-10-24，`draws: 0` 却 8 条 pass 通过）。

| 类 | 定义 | 能不能判红 | 本仓库的例子 |
| --- | --- | --- | --- |
| **结构量** | 期望值由设计定义，与机器、时间、相位无关 | **能** | `bodies === 15`、canvas 数量 === 1、`draws > 0`、`overflowX`、DOM 文本、**画布是不是全黑**（0 与非 0 的二值，是 `draws > 0` 的代理） |
| **观测量** | 期望值取决于机器状态 / 模拟时间 / 相位 | **只能记录** | `overlapping`（12–18）、帧时间绝对 ms、贴图总像素（0.79–0.82 M）、像素亮度的**具体值**（「应该 ≥ 8.9」这种）、NaN 的 id 名单 |
| **归一化观测量** | 观测量 ÷ 同一次运行内的参照量 | **能，但三个条件缺一不可** | `frame-time.normalized`（÷ 本次机器基线）、`proto-jitter.pp`（p10–p90 / 120 帧，对比 legacy 对照组） |

> 画布像素体检看着像「亮度判据」，其实不是：它问的是**画出来没有**（0 vs 8.9），
> 不是**画得好不好**。所以它的阈值 `meanLum < 2` 只是「0 与非 0」的分界线，
> 不是亮度标准——真按亮度定标准（比如「必须 ≥ 8.9」）就是观测量，只能记录。

归一化观测量要判红，三个条件缺一不可：

1. **同一次运行内自比**：分母必须是本次运行的机器基线或同一次采样的对照组，
   **不能**是跨机器的经验值，也不能是写死的常数；
2. **标定过余量**：有实测跨度，且阈值离实测值 ≥ 1.5×
   （`frame-time` 实测比值 0.41–0.61、阈值 1.6；`proto-jitter` 实测 5.2–6.5×、阈值 3×）；
3. **写明盲区与推翻条件**：抓得住什么、抓不住什么（`frame-time`：能抓 2.5× 以上的持续回归，
   抓不住 1.5× 的；`proto-jitter`：噪声底一变高就是几何/云层被改了，不是浮点问题）。

**一句判断法**：把这条判据红掉的几种可能写下来。**如果你说不清「红了该改哪里」，它就是观测量。**

**前置条件：能复现才有资格当判据。** 画布体检两轮实测稳定度 < 1.5%
（desktop 23.92→23.56、proto-real 12.12→12.11），所以它扛得住 4.5× 的阈值余量；
反过来，一个自己就抖 40% 的数字，什么阈值都救不了——先修测量，再谈阈值。

**前置条件之二：观测值必须连同它成立的前提一起报。** 凡是**相机中心漂移 / 屏幕偏移**这类数，
必须写明**指针停在哪**——实测同一份代码：指针在画面中心时漂移 **0**，停在角落时 **307.48px**。
没写指针位置的数字**不可比，也不许进结论**。

> 这条不是假想：一版里「滚轮朝指针漂移 0–0.1px」与「过渡段目标屏幕位移 126.5px」两条主指标
> 都是在**没写指针位置**的情况下报的，无法与任何别的测量对齐。钉死指针位置（固定在一处）复测之后，
> 同一份代码得到的是 **0 / 0** —— 两条旧数字从此只作为历史，不再被引用。

### 哪些数字不许当判据

`hit-matrix.overlapping`（屏幕距离 < 44 px 的重叠对数）**永远不判红**。按上面的分类，它是
**观测量**：随轨道相位浮动，2026-10-24 同一天 16 次运行实测跨度已达 **12–18**（同一份代码，
只是模拟时间不同）。一个会随模拟时间变的数字没有「好坏」可言——它红了，你既不知道该改相机、
改数据，还是改时钟。所以它只留在 `results` 里供人看趋势，**别给它加阈值**，包括「大致范围」这种软判据。

注意别把上面那个跨度也当成边界：`12–18` 是我这 16 次观察到的**跨度**，不是定义域——
真出现 20 也只说明相位不同，不说明坏了。要判断「重叠是不是变多了」，只能看同一时刻的
截图，或者把模拟时间钉死再比（那样只适合一次性排查，不适合当常驻断言）。

同一类数字还有个更要小心的：`texture-report.mjs` 里「聚焦后的贴图总像素」（0.79–0.82 M，
预算只升不降）也不是不变量，见下面「贴图预算与首屏」。

`hit-matrix.bodies` 则**要判**：探针契约是「挂载了几个天体就返回几条」，15 变了说明数据层漏天体；
有意增删天体时，改这里 + 本文件「探针契约」那张表。

**画布像素体检共挂在 5 条 pass 上**（`desktop` / `mobile` / `mobile-selected` / `single-file` /
`proto-real`，`judgeCanvasPixels` 2 个调用点），见下节「画布像素体检（抓整屏黑）」——
它抓的是「数据层全对、眼睛看到一片黑」这类回归。`proto-jitter` 另有独立回读，不计入这 5 条。

**手机 dpr 红线挂在 4 条 pass 上**（`desktop` / `mobile` / `mobile-selected` / `single-file`，
`judgeQuality` 1 个调用点，`run()` 里）——但**只在 `pointerCoarse === true` 时判**：
桌面 dpr=1 天经地义，硬抬到 1.25 等于凭空多烧 56% 光栅。实测（2026-10-24）：

| 视口 | pointerCoarse | 画布设备像素 / CSS | effectiveDpr | 判定 |
| --- | --- | --- | --- | --- |
| 桌面 1280×720 dpr1 | false | 1280×720 / 1280×720 | **1.000** | 不判 |
| 手机 390×844 dpr3 | **true** | 499×1080 / 390×844 | **1.279** ≥ 1.25 | **PASS** |

断言对象是**实测值**（`canvas.width / clientWidth` 由 DOM 现算），**不许**从配置读 `dprCap`：
上一版就是配 1.25、实测 1.249 —— `canvas.width = floor(390 × 1.25) = 487` → 1.249，红线被破了自己不知道。
这就是 T0 的 `dprCap` 写 1.28 的原因（390×1.28 = 499 → 1.279）。`__solarQuality` 探针**没了直接红**，
否则这条红线又回到「没有任何机器在守」的状态。

## 已知缺陷（记录但不判红）

> 这里只放**真 bug 未修**这一类。观测量与判据失效不走这里（见上两节）。

### 三态：PASS / FAIL / VACUOUS

- **FAIL** → 打印每条 `文件:行号: 内容`，退出码 1。
- **VACUOUS**：命中 0 且期望也是 0 —— **这不是通过，是判据失效**。重构把符号删干净之后，
  「数它还有几处」这种判据会真空变绿：将来用新名字复现同一份双真相，它照样全绿。
- **vacuous 为什么不判红**：R3/R6 之后 #3–#6 在当前代码上必然命中 0，判红会让这条命令**永远红**——
  本仓库有过先例：帧时间写死 `EMA ≤ 26ms`，忙机器天天红，红到最后没人看。
  所以 vacuous 打警告 + 计入汇总，退出码仍 0，**牙齿由 `--selftest` 保**。

### `--selftest`：证明护栏会红

`npm run check:shape:selftest` 在临时副本（`os.tmpdir()`）里**故意重引入**一份第二真相，
断言对应判据确实变红：注入 `simClock` 到 clock.ts、注入 `lookOf` 到 store.ts、注入 3 处
`spec.unit ===` 到 SolarCanvas……**每条判据各注入一次**（条数从 `CHECKS.length` 现算，不写死），任何一条注入后不红 → 退出码 1。
**跑不通的护栏不算护栏。** 判定用「原始命中数增加 + 状态变 FAIL」两个条件，
不能用显示条数——第 2 条通过时只展示函数外的命中，注入后显示数反而会变小（这个坑第一次跑就踩了）。

> **注入必须自证落到目标上。** 这条规则是三次同形翻车换来的：`raw` 不单调（越界时数值反而变小）、
> selftest 只会"往文件末尾追加"（改不动第一次出现的值）、只拷 `SCAN_FILES` 而判据读的是
> `README.md` / `package.json`（注入永远到不了）。三次的形状完全一样：**注入没落地，判据照样绿**，
> 于是 selftest 打印「✓ 会红」，而它证明的是一个不存在的东西。
> 所以现在：① 拷贝清单自证（拷完逐字节比对，不一致就 throw）；② 注入自证（改完读回来，
> 内容必须真的变了且含有注入内容）；③ **投不到就 throw，不许静默继续**。
> 这三条自己也要能被证明会触发——把注入的匹配串改成不存在的，必须看到
> `Error: [7] 注入无效：找不到 …` 且退出码 1（实测过）。

### 扫描范围：显式清单，不是递归 glob

`SCAN_FILES` 手写 19 个文件。`src/copy/**`、`dist/`、`release/` 里的字符串会污染计数，
第一次跑就会有人把脚本关掉。**新增 src 文件必须加进清单**——`[清单]` 那条 meta 判据会红并告诉你加哪个，
它防的是「新文件悄悄逃出扫描范围」（写这条判据的当天它就抓到了 `starfield.ts`）。

### 注释与代码怎么分开

`classify()` 是个小状态机：`//` 到行尾、`/* … */` 之内算注释；字符串与模板正文算**代码**（保守，宁多报）。
已知误判（换代码后要重看）：正则字面量里的 `//`、JSX 文本节点、`String.raw` 内容会被当成代码；
`"lookOf"` 这种字符串引用会计入命中（有意的，引用已删符号同样可疑）。
怀疑判错时用维护开关看分类结果：

```bash
node scripts/check-shape.mjs --dump src/solar/systems.ts      # 每行的代码/注释划分
node scripts/check-shape.mjs --dump-fn src/solar/systems.ts "function\s+tightenClipPlanes"  # 函数体行范围
```

> 第 2 条的函数体范围是**括号感知**的：参数里的类型字面量（`camera: { near: number }`）自带花括号，
> 只数花括号会在参数没结束时就配平、把函数体截成两行。已知限制：返回类型里带对象字面量时范围会偏短，
> 本仓库不触发。

改期望值的门槛只有一个：**能说清「旧期望为什么不再成立」**，并在本节记一行。因为红了就调，等于没有判据。

### 第 1 条不够硬：形状判据抓不住「公式写对了但用法错了」

典型反例：把 `tan(asin(R/d))` 改成 `tan(asin(R/d)/2)`，**计数不变、本脚本依旧全绿**，
而所有点击热区静默腰斩。所以第 1 条真正的护栏是**行为断言**：

- 同帧 `__solarProbe()[i].radiusPx` 对 `__solarPick.candidates()[i].radiusPx`，差 < 1e-6；

## 改语义之后：全仓扫旧说法

**规矩**：改了某个语义（字段变必填、默认值取消、行为改名、某个数字变了），**不要只改自己碰过的那一行**——
用 `Select-String` 把旧说法全仓扫一遍。注释过期从来不是孤例，是**成组**出现的：一处改对，
另外两处仍在断言旧行为，读者会按旧行为写代码。

```powershell
# 这台机器 PATH 里没有 rg，用 Select-String（等价：rg -c '旧说法' --glob '!node_modules'）
Select-String -Path (Get-ChildItem -Recurse -File -Include *.ts,*.tsx,*.md -Encoding UTF8 |
  Where-Object { $_.FullName -notmatch '\\(node_modules|dist|release)\\' }).FullName -Pattern '旧说法'
```

扫三样东西：**旧数字**（`512×256`、`7 张贴图`）、**旧名字**（`星轨`、`SANDBOX_LOOK`）、
**旧类型形状**（「可选」「没写就用默认」）。前两样好想，第三样最容易漏。

两个真实例子（同一类，都发生在 2026-10-24）：

1. **`spec.look ?? SANDBOX_LOOK` 已是死分支。** `SystemSpec.look` 改成必填（`systems.ts:77`
   `look: SystemLook;`）后，这个 `??` 对任何 typed 调用方都走不到，仓库里也没有 untyped 调用方。
   而 `SANDBOX_LOOK`（`systems.ts:55-64`）与 `SOL_SYSTEM.look`（`system-context.tsx:47-56`）
   现在是**两份逐字相同的值**，且没有任何代码校验它们一致——改了一边，另一边就成了谎，
   而它的注释还写着「当沙盘长什么样的参照物」。与此同时 `lookOf` 自己的注释仍说「没写就用沙盘的」。
   **结论**：建议删掉 `SANDBOX_LOOK` 与那个 `??`（改成 `return spec.look`），由 types 保证必填；
   保留的唯一代价是「一个没人用、但看起来像默认值的常量，会让人以为省略 `look` 是合法的」。
2. **`Hud.tsx` 两处同类过期注释**（早期 HUD 注释过期那次已改两处，勿再引用行号）：只改一处，另一处没人搜过。

## 画布像素体检（抓整屏黑）

**为什么要有这条**：2026-10-24 实测过一次「画布全黑但 8 条 pass 全绿」——`__solarReady` 置位、
canvas 数量对、DOM 文本对、`__solarProbe()` 的几何也对（`draws: 0, tris: 0`，一笔没提交）。
因为那些断言只验「数据层说得通」这一层，而用户眼睛看到的是黑的。当时真正抓住它的是
`proto-jitter` 的像素回读，纯属偶然。所以现在主 pass 也都带一条像素体检。

**覆盖几条 pass（数过的，别用记的）**：`judgeCanvasPixels` **只有 2 个调用点**——
`verify.mjs:405`（在 `run()` 里，覆盖 `desktop` / `mobile` / `mobile-selected` / `single-file`
共 4 条）和 `verify.mjs:610`（`proto-real` 1 条），所以是 **5 条 pass**：

```powershell
Select-String -Path scripts/verify.mjs -Pattern 'judgeCanvasPixels\(' | Where-Object { $_.Line -notmatch 'function ' }
# → 2 行：run() 里 1 个（覆盖 4 条 pass）+ proto-real 1 个
```

`proto-jitter` 另有**自己的一套**像素回读（`__solarPixels`，回读不到样本同样会红），
但它判的是抖动、不是亮度——**不算进这 5 条**，也别拿它的结论当「画布体检覆盖了 6 条」。

怎么验：读画布上 **25 个 8×8 块**（四角 + 中心），算平均亮度与非黑块占比。

- 判红条件：`meanLum < 2` **或** `nonBlackRatio < 0.5`
- 阈值标定（合成画布实测，两个方向都验过）：
  - 产品背景色 `#07090e` → `meanLum 8.94`、`nonBlackRatio 1.0` → **判绿**（4.5× 余量）
  - 纯黑 → `0 / 0` → 判红
- **前提**：`preserveDrawingBuffer` 必须为真，否则 `readPixels` 永远返回 0，会把「读不到」
  误判成「黑屏」。所以这几个 pass 的 URL 统一追加 `?diag=1`（`SolarCanvas` 的 `READBACK`
  由 `proto|legacy|diag` 触发）；万一属性不是 true，结果是 `available: false` + `reason`，
  **不判红**（宁可说测不了，也不冤枉产品）。
- `frame-time` 所在的数值页**故意不加** `diag`：`preserveDrawingBuffer` 会让每帧多一次拷贝，
  污染帧时间测量。那一页的「黑屏」由 `proto-jitter` 的像素回读兜底。

红了先看这条的 `canvasPixels`：`meanLum: 0` + `nonBlackRatio: 0` 就是整屏黑。
顺序是——先确认 `__solarProbe()` 的几何是否正常（正常说明数据层没坏，是渲染没画），
再看渲染器有没有提交（`?proto=1&diag=1` 的 `[proto]` 日志里 `draws`/`tris`）。

## 缩放预算与星空亮度（`zoom-budget`）

一条 pass 管三件事，三件分属两类判据（分类见上文「判据的三类」）：

| 判的量 | 分类 | 判据（都来自设计，不来自观察） | 阈值的由来（一次性取证，不是「当前值」） |
| --- | --- | --- | --- |
| 缩放到「太阳 3R」要几次 wheel | **归一化观测量** | ≤ 15（设计预算；目标是 ≤12） | 定阈值时实测 **11 次**（预算留 4 次余量） |
| 最深视距 / 太阳半径 | **结构量** | ≥ 1.2（禁止穿模） | 定阈值时实测 **1.200**（视距 4.56 = 1.2×3.8），贴线所以阈值不能再抬 |
| 星空边缘区平均亮度 | **归一化观测量** | ≤ 4 × 背景色亮度（=35.74） | 定阈值时实测 **14.12**（1.58× 背景），4× 是设计留的余量 |

**为什么「wheel 次数」能判红**：它问的是「从 A 视距到 B 视距要几次输入」，不读帧时间、不读像素，
与机器性能无关。但它**依赖输入节奏**——现在滚轮只改「对数视距目标」（`SolarCanvas` 里的
`zoomLogTarget`），目标按固定速率往前提、相机再按自己的跟随时间常数追上去，阻力只在「朝目标飞近」
那一侧生效。所以**没有"加速窗口"这个常量**，所谓加速是这套目标跟随的产物；
别按"冲量 + 衰减"去理解代码，代码里没有那个模型。

夹具的连发间隔由 `ZOOM_GAP_MS` 控制（**夹具常量，不是产品参数**），节奏由夹具说了算。
所以这里还记了 `maxGapMs`：单次间隔超过 `ZOOM_GAP_SUSPECT_MS` 时（说明机器卡到输入节奏散了）
按「环境抖动」不判红、只打提示——否则就是把负载误判成回归。

**星空采样区域怎么选**：画布**边缘 12 块**（4×4 网格跳过中央 2×2，每块 16×16 像素）。
中央坐着太阳/行星，任何全屏统计都会被天体亮度主导；「星星有没有抢戏」问的是背景区。
所以这条与「画布不是全黑」互补而不冲突：

- 全黑那条：**全画布 25 块**，`meanLum ≥ 2` —— 问「画出来没有」；
- 星空这条：**边缘 12 块**，`mean ≤ 4×背景` —— 问「星星抢不抢戏」。

实测两者分别是 23.56 与 14.12，本来就不是一个量，谁也不用迁就谁。
`median`（9.94）与 `max`（30.72）一起输出：中位数贴近纯背景，说明亮块是稀疏星点而不是整体过曝。

**背景亮度怎么来的**：`#07090e` 三个通道现算 `0.2126·7 + 0.7152·9 + 0.0722·14 = 8.94`，
不抄实测值。设计口径是「4 倍」——这个 4 来自设计，不是「现在测出 12 所以定 20」。
采样读的是**画布像素**，不含 DOM 暗角遮罩（星空画在画布上，设计口径也是画布）。

**判据依赖的钩子**：视距只能从 `__solarPick.candidates()` 的 `depth` 拿。
`__solarClip()` 的 near 在贴近时被 `nearMin`(0.06) 夹住、far 恒为 983，反推不出距离——
所以钩子没了就直接红（`readSunState` 的 `available:false` 会明确说「钩子没了就等于判不了」），
不会静默变成 0 通过。

## 太阳遮挡 / 启动分期 / 相机避让

三条新增（2026-10-24，太阳遮挡 / 启动分期 / 相机避让），**分类各不相同**，别一把尺子量：

| pass | 判的量 | 分类 | 判据 | 实测 |
| --- | --- | --- | --- | --- |
| `sun-occlusion` | 太阳被木星挡住时，木星盘面中心 24×24 的平均亮度 | **结构量** | ≤ **60** | **17.8**（Δ=7.6px，sun.depth 44.5 > 木星 12.5） |
| `boot-stage` | `?bootstage=1\|2\|3` 每期挂到的天体数、ready 时有无小行星带 | 半结构 | 天体恒 15；ready 时 belt 必须已挂 | 默认 ready 时 belt=true、15 个天体；stage1/2 belt=false、stage3 true |
| `camera-clearance` | 跟随月球**≥3 个**公转周期里，相机到**地心**的距离序列（分窗口；全方向口径读 `__solarCamera().nearest`） | **结构量**（第 2 周期起 `min ≥ 1.0`） | 第 2 周期起 **1.023–1.026**（擦在软钳目标线上）；第 1 周期 **0.944–0.983**（切换残差，只记录）；max **3.51–3.62** |

### 阈值 60 的依据

三个数一起看：**透亮核时 171.3**（阈值改前的实测）、**修好后 18.9**（改后）、**本轮独立复现 17.8 / 16.9 / 16.7**（三次）。取 60 的效果是
「离修好后 ~3.4× 余量、离坏掉的 ~2.9× 距离」——两边都不贴边。

**判别力是验过的，不是假设**：同一机位下，太阳在木星**前面**（Δ=66px，`sun.depth < 木星`）时中心亮度 **131.31**，
太阳在**后面**且对齐（Δ=7.6px）时 **17.8**。所以这条量的确实是「有没有穿透遮挡」，不是「中心本来就暗」。

**机位怎么来**：不硬编码像素坐标。先点 `#chip-jupiter` 让它成为跟随目标、等聚焦动画收敛；
再**几何摆位** `__solarPlace("jupiter", 12.5, 180, 0)`——方位角以「指向太阳」为 0°，所以 180° 就是
把相机放到木星**背光侧**、太阳落在木星正后方；最后才用小幅闭环拖动微调。
收敛判据不是某个 px 常数，而是**全遮挡**：`sunBehind && (deltaPx + 太阳屏半径) ≤ 木星屏半径`。

> 为什么换掉了旧的纯闭环：实测**拖 100px 会让太阳在屏幕上移动 302px**（`delta 18.7 → 283.7`，3 倍放大），
> 而旧环路增益 0.55、步长上限 260px ⇒ 单步能推近 780px，对 20–50px 的偏差**必然跨过头**，
> 于是 26 步里一路来回弹，最后停在 `deltaPx` 44.6 / 19.2（都在容差外）。
> 另外旧版还有个隐蔽问题：太阳一开始**根本不在候选里**（在屏幕外），"找回太阳"那支每次只拖 200px，
> 一整轮都在找而不是在对齐。

**实测（两次独立运行）**：`aligned: true`、`deltaPx` **26.1 / 25.7**、`coverSlackPx` **65.1 / 65.5**、
`centerBoxLum` **12.94 / 12.96**（cap 60）。也就是说这条判据现在**真的在判断**，而不是"诚实地说自己测不了"。
对齐失败时仍不判红，但由「连续 3 次未对齐」的护栏兜底（见上文 `runs/index.jsonl` 的 `unaligned` 字段）。

### 启动分期：`ready` 只在全量置位这件事怎么验

`Simulation ready={pin !== null || stage >= 3}`：**钉住期数（`?bootstage=N`）时 ready 依然置位**，这是设计注释写明的。
所以「ready 只在全量」只能在**默认路径**上验，可观测的量是 `__solarLook().mounted.belt`——
小行星带是第 3 期才挂的（`SolarCanvas` 的 `stage >= 3 && <Asteroids />`），
**ready 那一刻 belt 必须已经是 true**；若有人把 ready 提前到第 1 期，它会变 false 立刻红。
长任务只记录：这台机器上长任务判据分不出启动和稳态（已有结论），拿它判红就是重犯「26ms」的错。

### 相机避让：1.026 是「渐近目标」，不是硬钳线

`clampOutsideParent` 是**软滑出**：目标点仍是球面上最近的那个点（`父半径 × 1.35`），
但每帧只朝它走 35%（`camera.position.lerp(target, 0.35)`，≈3 帧走完 97%）。
改之前的硬钳是「一帧内 position = 球面点」：相机被母天体拖进球里再从径向弹出来，
画面像被顶了一下。**所以 1.026 不是「钳制没生效」，是「钳制从硬墙改成了软目标」。**

代价是：每帧被母天体拖进去的位移 δ 会留下约 `δ / 0.35` 的稳态残差。δ 由倍速和帧率决定，
所以软钳的「底线」不是一个常数——代码里也**没有**地心硬底线：
`controls.minDistance = max(1.15, 目标天体半径 × 1.2)` 管的是相机到**跟随目标（月球）**的距离，
不保护地球。

**采样纪律：≥3 个周期、分窗口报，判据只压第 2 个周期起。**

| 窗口 | 地心距离 min | 怎么用 |
| --- | --- | --- |
| 第 1 个周期（点进月球后） | **0.944–0.983** | **只记录**：切换残差，不是回归 |
| 第 2 个周期起 | **1.023–1.026** | **判红：min ≥ 1.0**（钳制线 1.026，留 2.5% 余量） |
| max（各窗口） | 3.507–3.621 | 只记录 |
| 单帧跳变 | max 0.032–0.058 / 中位 0.015 | 只记录（`jumpMaxPerSimUnit` 3.09–3.79 是换到同一模拟时间尺度重算的） |

混在一起取 min，会让同一份代码三次给出 0.94 / 0.98 / 1.03，被当成产品回归——**分窗口就是为了这个**。
`min ≥ 1.0` 的**阈值来源是产品的软钳目标线**（`父半径 × 1.35` 留余量），不是「现在测出来这么大」。

**口径修正**：旧表述「min 1.026 正好等于钳制线 → 钳制每次都在生效」**结论对、口径错**——
它是「稳态下每次擦边都擦在目标线上」，不是「硬钳每帧压住」，而第 1 个周期会低到 0.944。
另外 `__solarPick.candidates()` 会剔除相机背后的天体：地球在背后时 `earth.depth` 是 null，
那些帧会被**静默跳过**（真实 min 0.944、候选口径报 0.962，漏 1.9%）。所以「相机在不在天体内」
一律读 `__solarCamera().nearest`（全方向，带 `radius`）。

### 切换过渡段不在这条 pass 的稳态窗口里

`camera-clearance` 的判据覆盖的是**跟随稳态**。从「地球取景」点进「月球取景」的聚焦动画里，
`clampOutsideParent` 不跑（动画分支提前 return），插值路径可能穿过地球，动画结束后才被软钳滑出来。
实测（五次独立测量，**数值会漂，只信区间**）：地心最小落在 **0.53–0.98**，最差 **0.528**（地球半径 0.76），
越界时持续 5–11 帧 / 129–264ms，最低点在点击后 0.7–0.85s。相位决定穿不穿（同一份代码会红也会绿），
所以夹具用 `__solarTime.set()` 钉三个相位各跑一次、取最差；**判据只写「< 地球半径 0.76」，不写具体距离**。
这条**记录但不判红**——它是真 bug、还没修，明细与到期条件见「已知缺陷（记录但不判红）」。
这条现在是**硬断言**（到期条件已满足）：最小距离 < 1.0 × 天体半径就判红，不再有「只记录」的分支。

## 探针契约（`__solarProbe()` / `__solarTextures()`）

`__solarProbe()` 返回的**条数 = 当前挂载的天体数**（沙盘 15、`?proto=1` 3），
**不是**「画面里能看到的数量」。

**相机背后的天体返回 NaN 哨兵**：`x/y/z = NaN`、`radiusPx = 0`。
这是**有意设计，不是 bug**——拾取器那边把背后的天体剔掉（点不中、也不该出手型），
但探针保留一条记录，因为 `hit-matrix` 数 15、`proto-real` 数 3 这两条断言都建在
「条数 = 挂载数」上。更关键的是**不编造镜像坐标**：`project()` 在 z<0 时会翻符号把
背后的天体镜像回画面，看着在屏幕上、点了却没反应 —— 那正是「幽灵热区」那种毛病。

实测（`node scripts/texture-report.mjs`，加 `"?proto=1"` 参数换模式）：

| 场景 | 条数 | NaN 条数 | 是哪些 |
| --- | --- | --- | --- |
| 沙盘默认视图 | 15 | 0 | — |
| 沙盘聚焦地球后 | 15 | 6 | 示例 sun / mercury / mars / saturn / titan / neptune —— **具体哪几颗随相机状态变**，别当不变量 |
| `?proto=1` | 3 | 1 | sun（真的在相机背后） |

**看 verify 输出时有个坑**：`JSON.stringify(NaN)` 是 `null`，所以 results 里 `"x": null`
表示「这颗没有屏幕位置」，不是「探针坏了」。`hit-matrix` 的配对统计天然不受影响 ——
`NaN < 44` 恒为 false，NaN 条目不会进配对。

代码位置：`src/solar/SolarCanvas.tsx:1599-1607`（`Select-String -Path src/solar/SolarCanvas.tsx
-Pattern 'Number\.NaN, y: Number\.NaN' | Measure-Object` → 1）。

## 贴图预算与首屏（frame-time 为什么单列启动段）

1.1.2 之前是 `radius > 0.4 ? 512×256 : 256×128`，在 React 首次 render 里同步跑完：
**12 张 + 云层 = 1,114,112 px**，主线程一次阻塞 **380–500 ms**（注记在 `textures.ts:16-19`）。
现在切成两刀：`textureBudget()` 按屏幕占幅定尺寸（0.5 纹素/像素，128–2048 取 2 的幂，
见 `TEXELS_PER_SCREEN_PX`），像素循环按 `CHUNK_MS = 5` 分帧排队，每片落在下一帧 rAF 里。

实测（本机 1280×720，`node scripts/texture-report.mjs`）：

| 时刻 | `totalPixels` | 说明 |
| --- | --- | --- |
| `__solarReady` 瞬间 | **13** | 13 张全是 1×1 占位色，`pending=13`，首帧不阻塞 |
| 稳态总览位（~4s） | **106,496** | 13 × 128×64（`TEX_MIN_WIDTH` 档），`pending=0` |
| 聚焦地球后 | **≈0.79–0.82 M** | 两次实测 794,624 / 819,200，**不是定值** |

最后一行不稳定是设计使然：预算「只升不降」，聚焦动画期间谁上过屏就按谁的占幅升档，
两次运行的相机轨迹略有差别，升上去的档位就不同（`venus` 会到 1024×512、`clouds` 512×256）。
所以**别拿这个数当断言**；要断言就断 `pending` 归零、且每张不超过 `TEX_MAX_WIDTH` 档。

`?proto=1` 下 `__solarTextures()` 返回空列表（原型不生成程序化贴图），像素预算只对沙盘有意义。

这也是 `frame-time` **单列启动段、只判稳态**的原因：首帧要跑几何首建 + 13 张贴图排队，
一次性成本混进稳态，等于把「刹车」算成「车重」。

**启动长任务实测（`PerformanceObserver('longtask')`，导航前装，1280×720）**：首次长任务
`start 241.6ms / dur 129ms`（≈148ms 那个"地板"说的就是它），但**最长一条是 208ms @422.9ms**，
共 3 条，`__solarReady` 在 747.1ms。

> **地板 ≠ 上限。** 「首次长任务 ≈148ms」只描述**第一条**；启动期最长的一条能到 **208ms**（比地板高 40%）。
> 别拿地板当"启动期没有更贵的东西"的证据——那正是本轮差点犯的错。

## frame-time 的红线怎么读

判的不是绝对毫秒，是比值。**两个判据**共用一把尺子：分母 = 本次机器基线。

```
normalized.ema  = steady.ema ÷ denominatorMs   阈值 1.6
normalized.p95  = steady.p95 ÷ denominatorMs   阈值 2.5
hitch（超阈帧数）：只记录 + 告警，**不判红**（2026-10-24 改过判据，理由见下）
```

`denominatorMs` 取两次基线里较大的那个：一次在遥测页**开起来之前**测，一次在**关掉之后**测。
基线本身是两件事：

- `vsync`：`about:blank` 空 rAF 循环 → 这台机器当前的 vsync 节拍（本地实测 8.3–16.9ms 都出现过）
- `raster`：1280×720 全屏定量着色器页，每帧固定 8 个 pass → 当前可用光栅吞吐

分母 = `max(raster.ema, vsync.ema)`。空循环那一路是**兜底**：闲机器上 8 个 pass 可能塞进一帧、
被 vsync 钉住，这时断言自动退化成「场景 ≤ 1.6 × vsync」——没信息的时候不假装有信息。
p95 的 `2.5 × 分母` 和旧判据同源：60Hz 机器上 2.5 × 16.7 = 42ms < 50，所以 hitch 阈值仍按 50ms 地板算。

### hitch 为什么不再判红

它量的是「150 帧里有几帧超过 `max(50ms, 2.5 × 分母)`」，是**观测量**：被超的那几帧在共享机器上
主要由 CPU 争抢决定，跟产品改了什么没关系。实测证据（同一份代码、同一台机器）：

- peak 时 `median 34.3ms / 归一化 EMA 1.05（通过）`，却 `hitch 5 > 2`，同期 22 个浏览器进程，**重跑即绿**；
- 本机 10 次历史运行里 `baselineHitches` 常为 0，而场景仍可能 5 次 ——
  所以「按基线占比归一化」这条路**救不了**（0 的倍数还是 0），先排除。

它原有的信号已被归一化的 `EMA`（≤1.6×）与 `p95`（≤2.5×）覆盖：那两条是同一次运行内自比、
标定过余量、盲区写明的。**没有放宽任何阈值数字**，改的是判据类型。

**代价（必须知道）**：`<5%` 帧的**稀疏卡顿不再判红**——p95 是 95 分位，管不到 2% 的尖峰。
真要看这类问题：`normalized.hitch` / `hitchExceeded` 仍在 results 里，超告警线会打一行
`（注意）frame-time: 稳态 hitch N 次 > 告警线`；连续多次都超时再怀疑产品侧的周期性阻塞（贴图重建之类）。
若将来要把它重新变成判据，建议用「场景 p95 × 1.5」当阈值而不是绝对次数——那才是同一条分布内的自比。

红了先按这个顺序看：

1. `baseline.before.raster.ema` 和 `baseline.after.raster.ema` 差得远吗（比如 40 vs 20）？
   差得远 = 采样这段里机器状态变了，先重跑，别急着改代码。
2. `normalized.ema` 是多少？1.6 出头可能是真毛刺，**1.8 以上且两次基线接近**才是真回归
   （单帧光栅量真涨了，比如有人往每帧里塞了贴图重建）。
3. `steady.ema`（绝对 ms）和 `legacy.wouldFail` 只是留档：`wouldFail: true` 但全绿是**正常**的，
   它记录「旧规矩在同样这份采样上会红」，用来对比，不参与判定。
4. `normalized.hitch` / `hitchExceeded`：只作趋势与告警；同一把尺子量基线页的
   `baselineHitches` 也不为 0 时，说明这台机器整体在抖，那几帧更不能算产品的账。

阈值 1.6 的来历写在 `verify.mjs` 顶部注释里：旧断言 `EMA ≤ 26ms` 在 60Hz 机器上等于
26/16.7 = 1.56×，新阈值取 1.6 保持同等严格度。

**这条断言的已知盲区（别指望它能抓小回归）**：实测「场景÷基线」在同一个代码版本上
摆到 0.44–0.90（忙时 0.44–0.61、加压 0.48、闲时 0.55；更早一轮探针里到过 0.90）。
阈值 1.6 意味着：**能抓住 2.5× 以上的持续光栅量回归，抓不住 1.5× 的**——那是噪声。
要比「两倍以内」更细的结论，只能关掉机器上别的东西、在安静状态下用绝对阈值复核，
不要指望这条相对断言。什么时候它会被推翻：如果哪天场景÷基线稳定收敛到 0.6±0.05
（比如把基线页成本调到跟空闲场景成本接近），阈值就该往 1.0 收，那时它能抓到 1.6× 的回归。

## proto-jitter 的维护契约

这条 pass 有四个**非显然依赖**，动任何一个都会**静默失效**——不报错，只是测不出东西。
（同样的说明也写在 `verify.mjs` 那段注释里，改代码前两边对一遍。）

1. **断言值绑当前实测，且绑估计量**：`modern.pp < 0.35`、`legacy.pp > 3 × modern.pp`、`legacy.pp > 0.2`。
   估计量是 **p10–p90 / 120 帧**（2026-10 从 max−min / 60 帧换过来的：max−min 只由两个离群点决定，
   测的是运气）。换后三次连续实测：modern 0.073–0.079、legacy 0.408–0.474，比值 5.2–6.5×。
   `max−min` 的口径仍输出在 `ppFull` 里（0.13–0.15 / 0.66–0.87），只留档不判定。
   ⚠ **legacy 下限从 0.4 挪到 0.2 是跟着估计量换算的，不是放宽**：0.4 是按 max−min 定的，
   换 p10–p90 后整体数值下移约 40%，0.4 离实测最小值只剩 2%，必然误红；0.2 保留了原来
   「约 2× 余量」的设计意图，真正负责区分的是 `3×` 那条。**再换估计量时，三个阈值要一起换算。**
2. **视口必须钉死 1920×1080，且 `dist = 1.2e7`**。这个距离是反解出来的：再近，圆盘左右缘
   出画面就测不到边缘；再远，f/视距 变小、信号被噪声吃掉。
3. **背景色不能写死** `#07090e`：输出色空间是 sRGB，`setClearColor` 的值会先转线性（实测落在
   8.94 亮度），采样器是从四角 4×4 块**实测**背景的。
4. **原型里必须关掉云层壳**（`spec.unit !== "meter"` 那个条件）**并冻结自转/公转**。
   那个 1.02× 半透明壳会把圆盘轮廓偏移 8px、噪声从 0.1 抬到 0.6px；自转会把贴图暗区
   转进转出遮罩，实测拉动质心 10–18px。开着任意一条，这条断言就废。

调试入口：`?proto=1&still=1` 是相机钉死状态，噪声底应在 0.08–0.10px；
**如果噪声底本身变高，是几何细分或云层开关被改了，不是浮点问题。**

## CI 与本地差异

**CI 跑两道静态闸，不跑 verify。** `.github/workflows/build.yml` 在 `npm run build` 之后、
上传/发布之前依次跑这两条：

| 闸 | 命令 | 什么时候红 |
| --- | --- | --- |
| 1/2 | `npm run check:shape` | 任一条「同一个概念不许有第二份真相」FAIL，或 `[清单]` 与 `src/` 对不上 |
| 2/2 | `npm run check:shape:selftest` | 注入第二真相后，哪条判据没变红就红——它证明闸 1 的牙齿还在 |

两条都是零依赖纯 node、秒级，**没有 `|| true`：红了就拦**。
这一波（真实轨道 / 目标跟随 / 过渡钳制 / 新增 3 条 pass）之后 CI 仍然只跑这两道静态闸 + 闸 3 的
**版本号对账**（`releases/latest` 与 `package.json` 一致，避免产物顶着已发布的旧号），
`npm run verify` 依旧是**本地闸**（22 条 pass，需要真实浏览器与 GPU，约 160s）——CI 不跑它的原因见下。闸 1 的输出会整段进
`GITHUB_STEP_SUMMARY`，其中包括那 4 条 **VACUOUS**——它不是通过，是判据失效，CI 里必须让这句话
可见（但不因为它判红，判红会让这条命令永远红在同一个地方，红到最后没人看）。

**CI 为什么不跑 `npm run check`：** 它 = `check-single-file.mjs && check-shape.mjs`，
而 `check-single-file.mjs` 会 `chromium.launch` 一个**真实浏览器**。ubuntu-latest 上没有浏览器，
`browserType.launch` 抛未捕获异常 → 退出码 1，**每次 push 都假红**（实测：把 `XG_EDGE` 指到
`/nonexistent/msedge`，输出 `Failed to launch chromium because executable doesn't exist`，退出码 1）。
脚本侧已经支持 `XG_EDGE`，所以接它只差「给 runner 一个 chromium」这一个决定。

**CI 为什么不跑 verify：** 13 条行为验收要 **真实浏览器 + 软光栅（swiftshader/llvmpipe）+
本机帧时间基线**。前两个是安装问题，第三个不是：`frame-time` 的阈值绑在本机实测基线
（`modern.pp < 0.35` 那组数）上，换机器不重测基线，红绿都不可信。

**将来接 verify 需要的两个前置条件**（缺一不可）：

1. **runner 上有 chromium**，并让脚本用 `XG_EDGE` 指过去（`verify.mjs` 已读这个变量）；
2. **一份 CI 自己的帧时间基线**：在 runner 上采一次 `?proto=1&still=1` 与默认场景的基线，
   把阈值绑到「CI 基线 / 本地基线」的**比值**上，而不是任何一方的绝对值。

接 verify 时还要知道这四件事：

- **都是软件光栅**：CI runner 没独显，WebGL 走 llvmpipe/swiftshader；本地 Edge 也被强制
  `--use-angle=swiftshader`。两边同一类渲染路径，这是「基线比值」能跨机器迁移的前提。
- **rAF 都被 vsync 钉住**：CI 是虚拟显示器，基本恒定 60Hz（16.7ms）；本地这块面板实测
  出现过 10.3 / 16.7 / 8.3ms 三种中位数（高刷/动态刷新）。所以任何「默认 60Hz」的绝对阈值
  在本地都会失真——这也是 frame-time 不许写死 ms 的直接原因。
- **CI 更慢但更稳，本地更快但会被别的进程抢**。基线法两边都能吃；反过来，写死绝对阈值
  在两边都会误判（CI 偏红、本地偏绿）。
- **同机并行**：并发构建和并发 verify 都会污染结果，见下面「别和别人的构建撞车」。

**规则：量帧时间一律用 `release/site` 的静态服务，不走 dev server。** 不是偏好，是事故：
dev server 的 HMR 在别人改 `Hud.tsx` 时会**整页 reload**，采样被从中间打断，那一组数据直接作废
（实测被削成 0 条样本）。verify 与本目录的测量脚本都自己起静态服务器，就是为了让「被测量」
只有产品本身，不掺构建工具。

## 别和别人的构建撞车

`release/` 不是只读的：`npm run build` 会先 `rm -rf release/` 再整份重建，整个过程一两秒。
如果**别人正好在跑构建**，你的 verify 会抓到半成品，症状很有迷惑性：

- `画布没起来（__solarReady 未置位）` + `控制台 404`
- 或者干脆来个 `pageerror: XXX is not defined`（页面拿到的是上一版 index.html、加载的是新版 JS）
- **而且每次红的 pass 不一样**（这次 desktop、下次 mobile-selected）——这是撞车的指纹，
  不是产品 bug

判断方法：看 `release/site/index.html` 引用的 `assets/*.js` 是不是真的存在，以及
`release/site` 的时间戳是不是落在你这次运行的时间窗里。确认是撞车就**别改代码**，重跑。

要拿到确定性结果，先冻一份快照再验：

```bash
cp -r release .tmp-release-snap          # 快照（.gitignore 已忽略 .tmp-*）
XG_RELEASE=.tmp-release-snap npm run verify
rm -rf .tmp-release-snap
```

另外，**两台 verify 同时跑也会互相污染**：双方的全屏 WebGL 互抢光栅，
`frame-time` 的分母会把对方的开销算成「机器基」。端口不会撞（自动往后找），CPU 会。

## 运行归档（`runs/`）：让失败证据活过终端

每次 `npm run verify` 结束都会把**整份 results + 环境指纹**写进 `runs/`：

- `runs/<时刻>__<build 哈希>__<光栅>.json`：那一次的完整结果（含 `knownBug` 之类的记录字段）；
- `runs/index.jsonl`：一行一次运行，字段固定（`at / build / raster / passes / failures / failureNames / knownBugs / viewports / file`）。

**为什么要有它**：`sun-occlusion` 的 `centerBoxLum` 与 `aligned` 曾经只活在一条消息里——全仓 `*.json` 搜它 0 命中，
于是「这条判据从哪一版开始不对」回答不了，只能靠记性。归档之后那是一句：

```powershell
Select-String -Path runs\index.jsonl -Pattern 'sun-occlusion'   # 哪几次红、红的 build 是哪个
node scripts/verify-archive.mjs --list                          # 人看的历史列表
```

三条硬约束（都是踩出来的）：

1. **归档失败绝不让 verify 变红** —— try/catch 包住、只打警告。测量工具不该吃被测结果的账。
2. **索引字段固定** —— 它就是"用 Select-String 查历史"的接口，改名等于悄悄废掉所有历史查询。
3. **保留策略写死**（最近 **40 次 / 30 天**，先到先清）—— 不写保留策略，一年后就是几百 MB 垃圾。
   只清 run 文件，**`index.jsonl` 永不删**（历史不能丢）。

开关：`--no-archive` 或 `XG_NO_ARCHIVE=1` 可跳过归档（会打印「本次不写归档」，不静默）。
`runs/` 已在 `.gitignore` 里；**归档不进 git**。
归档器自带离线自测：`node scripts/verify-archive.mjs --selftest`（不开浏览器，含「写不进去时会抛」的正向证明）。

## 夹具与自动收起（`hudAutoHide` 之后的硬规则）

自动收起默认开着，它改了两件夹具必须知道的事。**这不是"注意事项"，是照着做才跑得通的规则**：

1. **收起是卸载，不是 `display:none`。** 芯片行会被从 React 树里拿掉，只剩把手。所以
   `locator()` **每次都要重新取**，不许缓存——缓存下来的 handle 在收起后就是死的，
   点它会得到 `element was detached from the DOM`。本仓库对「不显示」的一贯口径就是结构上不存在
   （`display:none` 会留下看不见但可聚焦、可被 `querySelector` 命中的幽灵）。
2. **唤醒区只有边缘带，不是"任何 pointermove"。** 指针必须落进
   `[data-hud-chrome="top"]`（收起态高 **104px**）或 `[data-hud-chrome="dock"]`（收起态高 **53px**）
   的矩形里才唤醒；移到画面中央（比如 `(640,300)`）**永远唤不醒**——那正是设计意图：
   看场景时 chrome 不该跳出来挡视线。所以夹具的点击顺序必须是：
   **`mouse.move` 到唤醒带 → 等 ~300ms → `locator()` 重取 → 点**。
   另外展开动画约 250ms，`waitForSelector(..., {state:"visible"})` 在这期间会短暂失败，**要带重试**。
   （实测代价：不按这条写，夹具会在 40 秒内挂在 `element is not stable` → `detached`。）
3. **桌面卡片的高度是流动的，别把它当常量断言。** 卡片锚在场景带上下沿
   （`md:top-4 md:bottom-4`），所以 **卡片高 = 场景带高 − 32px**：
   顶部区 160 + 底栏 153 → 场景带 407 → 卡 **375**；底栏收起成 53 后 → 场景带 507 → 卡 **475**。
   同一份内容、只是容器高了 100px。**要一个稳定的卡片高度，先把指针放到顶部区把 chrome 钉成展开态。**
   桌面卡另有自己的结构钩子：展开态「收起」条 `button[aria-label="收起详情卡"]`（h=28）、
   收起态窄栏 `button[aria-label$="详情"]`（h=53）——`button[aria-label^="详情卡高度"]` 那套是**手机抽屉**
   专用的三档把手，桌面卡没有。

## 测量夹具不许复用产品数据

**一次"正确的物理改动"会静默废掉一条浮点断言**——真实发生过：把 `REAL_PROTO_BODIES` 从圆轨道换成
J2000 六根数之后，`proto-jitter` 的 modern 从 **0.073px 涨到 2.756px**。根因不是浮点量化，
而是 proto 夹具的**可见贴图相位**变了（地球从 +X 圆轨道换到 J2000 位置，滚转扫的是另一条经线），
像素回读对比到的抖动根本不是顶点精度。当时看起来像"精度回归"。

所以：**夹具自己持有它需要的输入，不复用产品数据。** 同一个概念的两种用途要拆成两份常量
（那次的做法：`REAL_PROTO_BODIES` 留给 `?proto=1` 的旧圆轨道 3 体，产品实境另用 `REAL_SYSTEM_BODIES`）。
理由和整份文档一致：**一个数据两个用途，改一个用途就会悄悄改另一个用途的判据**。

判断标准很简单：**如果产品的某个改动"按理不该影响这条断言"，但夹具读了产品数据 —— 那它一定会影响。**
遇到这种断言，先把夹具的输入钉死，再谈判据。
